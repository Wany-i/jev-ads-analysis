# 07 · 集成与载体

> **给「要照着跑起来 / 要改集成」的人。**
>
> 结论先行：分析结果里有三样东西需要**并排看** —— 规则层结论 + 可追溯依据、Jev 的第二意见
> （动作 / 置信度 / 紧迫度 / 无效花费概率）、以及**处置**（自动执行 / 人工复核 / 待标定）。
> 散在 JSON 里没法用，所以选**飞书多维表格**当载体：一层筛选视图就能把「分歧案例」挑出来。
> 同步走 `lark-cli`；取数除了 CSV 还有**剪贴板通道**。

- 代码在本仓库 [`jev-ads-analysis`](../../)；模块职责见 [`06-实现说明`](06-实现说明.md)。
- 标记约定沿用 [`00-阅读指引`](00-阅读指引.md)：**事实** = 代码 / 实测 / 上游文档可查；**推断** = 本文作者的判断。

## 一、为什么用多维表格当分析载体

`bitable_sync.py` 的模块注释写得最直白 —— 三条理由（**事实**）：

1. **分歧案例需要人看**：表格天然适合筛选 / 分组 / 批注。
2. **一层「是否分歧」筛选视图**就能把需要复核的案例挑出来。
3. **规则层依据与 Jev 输出并排**：人能直接对比两层的判断，而不是只看一个结论。

需求与能力的对照（本仓库 `docs/02-分析载体-飞书多维表格.md` 整理）：

| 需求 | 多维表格的能力 |
|---|---|
| 把「分歧案例」挑出来 | 一层 `是否分歧 = true` 的筛选视图 |
| 按优先级处理 | 按 `规则层优先级`（P0/P1/P2）分组 |
| 并排对比两层判断 | 字段天然并排，无需拼接 |
| 留痕 | 记录级历史 + 评论（**本项目未验证**，见 §九） |

**为什么不是别的载体**（**推断**，本文作者判断）：Jev 的输出是「动作 + 概率」，规则层的输出是
「动作 + 一句可复算的依据」，两者放在同一行才有人能读的对比价值；换成纯 JSON 或日志，
人就得自己在脑内做 join。

**已验证实例**（2026-09-21，事实）：

| 项 | 值 |
|---|---|
| 地址 | `https://cathypromotion.feishu.cn/base/V2XMb01AfahmKYsDDahcIXiZn3f` |
| base_token | `V2XMb01AfahmKYsDDahcIXiZn3f` |
| table_id | `tbl4UjaTh0wFfHnE` |
| 字段数 | 24 |
| 已写入记录 | 7（示例数据） |

## 二、表结构

主表是 `关键词判断`，**24 个字段**（事实，与 `src/base-schema.json` 一一对应）：

| 分组 | 字段 | 类型 | 来源 |
|---|---|---|---|
| 输入 | `关键词` | text（主字段） | 报表 |
| 输入 | `站点` / `匹配方式` | select | 报表（匹配方式做归一） |
| 输入 | `曝光` / `点击` / `花费` / `销售额` / `订单` / `运行天数` / `当前出价` | number | 报表 / 命令行兜底 |
| 代码计算 | `目标ACOS` / `实测ACOS` / `盈亏平衡ACOS` / `可接受CPC` / `动态点击阈值` | number | `state_builder` / `pipeline` |
| 规则层 | `规则层动作` / `规则层优先级` | select | `rule_layer` |
| 规则层 | `规则层依据` | text | `rule_layer`（**可追溯**，这是核心资产） |
| Jev 影子层 | `Jev动作` | select | `jev_shadow` |
| Jev 影子层 | `Jev置信度` / `Jev紧迫度` / `无效花费概率` | number | `jev_shadow` |
| 比对 | `是否分歧` | checkbox | `compare` |
| 比对 | `处置` | select | `compare` |

**select 的合法选项**（事实，取自 `base-schema.json`）：

| 字段 | 选项 |
|---|---|
| `站点` | US / UK / DE / JP |
| `匹配方式` | 自动 / 广泛 / 词组 / 精准 / 商品投放 |
| `规则层动作` | 加价 / 降价 / 暂停 / 保持 / 否定 |
| `规则层优先级` | P0 / P1 / P2 |
| `Jev动作` | 加价 / 降价 / 暂停 / 保持 / 否定 / **未接入** |
| `处置` | 自动执行 / 人工复核 / 待标定 |

几条**写入约定**（事实）：

- **比例类字段按小数写**（`目标ACOS = 0.25` 表示 25%），同步时会四舍五入到 4 位小数；
  想要百分比显示，在表里加一个公式列，不要改字段本身。
- `是否分歧` 用 checkbox（布尔），方便直接做筛选视图。
- 三个 Jev 输出字段**带字段注释**（鼠标悬停字段名可见）—— 注释内容就是 `src/base-schema.json` 里的
  `description`，语义说明见 [`05-字段说明`](../05-字段说明.md)。
- **不要把真实店铺数据提交到仓库**：同步是运行时行为，不产生任何仓库文件。

## 三、三个筛选视图

**已验证实例建了 3 个视图**（事实，本仓库 `docs/02-分析载体-飞书多维表格.md` 的实测记录）：

| 视图 | 视图 ID | 过滤条件 | 用途 |
|---|---|---|---|
| **待复核** | `vewCjBeR2o` | `处置 == 人工复核` | 主要工作面 |
| **分歧案例** | `vewN8IMIXM` | `是否分歧 == true` | 分析两层为什么不同 |
| **P0止血** | `vew3p6bOgo` | `规则层优先级 == P0` | 优先处理 |

**为什么是这三个**（**推断**）：「待复核」是日常工作入口，「分歧案例」是影子层的价值出口
（两层不一致 = 这个案例确实模糊），「P0止血」是按后果排序的应急入口。三个视图分别对应
「谁要动手」「为什么值得看」「先动哪个」。

**注意（事实）**：本仓库 `docs/02-分析载体-飞书多维表格.md` 的「建议视图」列表里还有第四个 —— `处置 = 待标定`（标定 Jev 前的工作清单），
但**已验证实例里没有这一项**。所以实际是 3 个视图，不是 4 个。

## 四、同步的实际流程

`bitable_sync.py` 只做**一件事**：把 pipeline 输出的 `rows` 批量创建成记录。流程：

```bash
# 1) 先出分析结果（见 06-实现说明 第三节）
python src/pipeline.py --input <报表> --price ... --out output/pipeline-output.json

# 2) 干跑：只数将要写入的记录数，不调 lark-cli
python src/bitable_sync.py --base-token <token> --table-id <id> \
  --input output/pipeline-output.json --dry-run

# 3) 真写入
python src/bitable_sync.py --base-token <token> --table-id <id> \
  --input output/pipeline-output.json --as user
```

代码路径（事实）：`main()` 读 JSON → 取 `data["rows"]`（顶层就是数组时直接用）
→ `sync()` → `build_payload()` 包成 `{"create_records": [...]}` → `_resolve_cli()` 定位 CLI
→ `subprocess.run([...])` 调 `lark-cli base +record-batch-create` → 打印返回的 JSON。

| 参数 | 说明 |
|---|---|
| `--base-token` / `--table-id` | 目标表的定位（必填） |
| `--input` | pipeline 输出的 JSON |
| `--as user` / `--as bot` | 以哪种身份写入，默认 `user` |
| `--dry-run` | 只返回 `{"ok": true, "dry_run": true, "count": N}`，不调 CLI |

**返回与退出码**（事实）：CLI 返回非 0 或返回体解析失败时，`sync()` 返回
`{"ok": false, "returncode": ..., "stderr": ..., "stdout": ...}`，`main()` 据此返回 1。

**已知限制（事实 + 推断）**：代码里只有 create，**没有去重、没有 update**。
重复跑同一次分析会重复创建记录（**推断**，未实测，见 §九）。

## 五、同步踩过的 5 个坑

这五条都是**实跑踩到才发现的**，纯看文档发现不了：

| # | 坑 | 现象 | 修法 | 落点 |
|---|---|---|---|---|
| 1 | **载荷形状** | 写入失败 | 必须是 `{"create_records": [...]}`，**不是裸数组** | `build_payload()` |
| 2 | **select 的 CellValue** | 写入失败或类型错 | select 必须传**数组**：`["US"]` 而不是 `"US"` | `_to_record()` |
| 3 | **枚举值拼写** | 建表失败 | 颜色是 `Gray` 不是 `Grey` | `src/base-schema.json` |
| 4 | **权限名** | 授权失败 | 是 `base:view:write_only`，**不存在** `base:view:create` | lark-cli 授权 |
| 5 | **Windows 下 `.cmd` + 长 JSON** | `cannot find the file specified` | **必须改用原生 `.exe`** | `_resolve_cli()` |

展开说第 5 条（最隐蔽的一条）：Windows 上 `.cmd` 会经 `cmd.exe` **二次解析命令行**，
短参数时没问题 —— 一旦 `--json` 载荷是几千字符的中文 JSON，cmd.exe 的引号规则就会把命令行拆坏。
所以 `_resolve_cli()` 优先找 `lark-cli.exe`；找不到 `.exe` 时，才会退回 `.cmd` 路径，
并按 npm 全局布局去猜 `<prefix>\node_modules\@larksuite\cli\bin\lark-cli.exe`。

**补充第 6 条（事实，`CHANGELOG` 有记）**：**非法 select 值会让整批写入全部失败**。
实测背景：redhen 数据集里自动广告的 `Match Type` 是 `-`，不在 `匹配方式` 的选项里，
一个非法值就让 45 条全部失败（API 报 `not_found: Provide an existing option value`）。
修法是加 `VALID_SELECT` 白名单 —— **非法选项直接跳过该字段，宁可少写一个字段，也不要整批失败**。

## 六、剪贴板取数通道

**场景（事实，代码注释）**：RPA（影刀 / 紫鸟 Hubu / 自研脚本）把广告报表复制到剪贴板，
流水线直接从剪贴板取数，**省掉「导出文件 → 找文件 → 上传」三步**。

**怎么用**：

```bash
# 先把报表（Excel 选区或网页表格）复制到剪贴板
python src/pipeline.py --input clipboard --price 39.99 --cost 8 --out output/a.json
# 也可以写 clip；--input 是文件路径时走原来的文件通道
```

**处理流程**（事实，`pipeline.run()` + `clipboard_io.py`）：

1. `--input` 的值是 `clipboard` / `clip` → 走剪贴板分支
2. `read_text()` 读纯文本；空则报「剪贴板为空」
3. `looks_like_table()` 粗判：至少两行、首行含分隔符且至少 3 列 —— 不满足则报错并回显首行前 120 字符
4. `sniff_delimiter()` 判分隔符（首行制表符数 ≥ 逗号数就按 TSV，否则 CSV）
5. **先把剪贴板内容快照落盘**到 `output/clipboard-input-<时间戳>.tsv|csv`，再把快照路径当输入

**为什么要快照（事实，代码注释）**：`--out-clipboard` 会把结果写回剪贴板，覆盖输入数据；
落盘之后输入可复现，也能直接 `--input <快照文件>` 重跑。

**实现细节（事实）**：用 PowerShell 的 `Get-Clipboard -Raw` / `Set-Clipboard`，
**必须显式设 `[Console]::OutputEncoding` / `InputEncoding = UTF8`**，否则中文按系统 OEM 代码页
（简中 GBK/936）读写会乱码；写入走 stdin（避免命令行长度与转义问题）；`available()` 要求
`os.name == "nt"` 且能找 `pwsh` 或 `powershell`，否则明确抛错、不静默降级。

**安全**：剪贴板内容被当作**不可信输入** —— 只当表格文本解析，不执行其中任何内容（事实，代码注释）。

**写回结果时的备份**：`--out-clipboard` 在覆盖剪贴板之前，会先把原有内容备份到
`output/clipboard-before-write-<时间戳>.txt`。**血泪教训（事实，代码注释）**：
实测时这个动作覆盖掉了用户放在剪贴板里的 API 凭据。

**取数通道的优先级**（事实，来自 `amazon-ads-optimization/references/data-integration.md`）：

| 优先级 | 通道 | 前置条件 |
|---|---|---|
| 1 | 本机已装的亚马逊广告 API 数据技能（如 `ziniao-amazon-ads-system`） | 店铺完成 Ads 平台授权 |
| 2 | Linkfox 等第三方数据服务 | 账号 + API Key |
| 3 | 用户手动导出 CSV | 任何情况都可行，兜底 |
| 0 | 品牌分析 SQP 报告（定位份额短板） | 需品牌备案；无备案则跳过 |

**禁止**：抓取亚马逊卖家后台 / 广告后台页面来取数 —— 合规与稳定性都不可接受（事实，同上）。
`ads_opt.mjs` 认的列名（大小写不敏感、允许中英混用）也在那份文档里。

## 七、外部依赖要求

| 依赖 | 什么时候需要 | 要求 | 不满足时 |
|---|---|---|---|
| **Python** | 总是 | 3.10+，**无第三方依赖** | — |
| **lark-cli** | 只有同步到多维表格时 | 已安装并登录；具备 `base:record:create` 等写权限；建视图还需要 `base:view:write_only`；Windows 上要能解析到**原生 `.exe`** | `sync()` 抛「未找到 lark-cli，请先安装并登录」 |
| **OpenRouter** | 只有 `--jev live` 时 | 环境变量 `OPENROUTER_API_KEY`；端点 `https://openrouter.ai/api/alpha/decisions`；模型 `typesafe/jev-1.13` | 不改 default：dry-run 照常跑通，Jev 列输出「未接入」、处置列「待标定」 |
| **Node** | 只跑 JS 版规则层时 | 18+（`ads_opt.mjs`，零依赖） | — |
| **PowerShell** | 用剪贴板时 | Windows + `pwsh` 或 `powershell` | `ClipboardUnavailable`（明确报错，不降级） |

几条必须知道的细节（事实）：

- **`lark-cli` 路径在模块导入时解析一次**（`CLI = _resolve_cli()`），所以换 PATH 之后要重开进程。
- **lark-cli 不能用 `.cmd` 传长 JSON**（见 §五 坑 5）。
- **OpenRouter 的 Key 只从环境变量读**，代码不落盘、不写进输出文件。
- **Jev 不能走 `chat/completions`**：decisions 端点在 alpha 路径下、没有 `/v1`。
- 调用对 **5xx / 429 / 网络超时**最多尝试 3 次（退避 2s、4s）；4xx（除 429）不重试。

**保密约定**（事实，来自 `data-integration.md`）：只输出业务可读名称与结论；
不输出内部 profile ID、代理地址、密钥、原始 JSON；币种与时间窗必须标注；跨店铺数据不混用。

## 八、这个集成不做什么

- **不做任何写操作到广告后台。** 输出是给人看的分析结果，不是自动调价机器人（事实，`README`）。
- **不自动改广告**：`bitable_sync` 只往表里写记录；真正动广告要人按表里的动作去执行。
- **不在未标定时启用 Jev 门控**：`--jev` 默认 `dry-run`，未标定就输出「未接入 / 待标定」，
  而不是猜一个结论（理由见 [`06-实现说明`](06-实现说明.md) §四 4.6）。
