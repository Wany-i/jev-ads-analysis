## 一、代码结构与数据流

| 文件 | 职责 | 关键入口 |
|---|---|---|
| `src/state_builder.py` | 读报表 → 算全部派生量 → 裁剪成 Jev state | `load_rows()`、`Economics`、`TermRow.to_jev_state()` |
| `src/rule_layer.py` | 规则层硬阈值判断，每条结论都带依据 | `judge()`、`judge_all()` |
| `src/jev_shadow.py` | 调 Jev 或干跑；解析三类输出；门控 | `judge_all()`、`parse_answers()`、`_gate()` |
| `src/compare.py` | 分歧检测 + 处置判定 + 汇总 | `compare()`、`summarize()` |
| `src/bitable_sync.py` | 把结果同步到飞书多维表格 | `build_payload()`、`sync()` |
| `src/pipeline.py` | 编排入口（CLI） | `run()`、`main()` |
| `src/clipboard_io.py` | 剪贴板读写（仅 Windows） | `read_text()`、`write_text()` |
| `src/sweep.py` | 阈值扫描与曲线（标定用，独立脚本） | 直接运行 |
| `src/base-schema.json` | 多维表格字段定义（含字段注释） | 数据文件 |
| `tests/test_rules.py` | 回归测试（标准库 `unittest`） | `python -m unittest discover -s tests -v` |
| `tools/run_checks.py` | 一键跑全部检查（等价 CI） | `python tools/run_checks.py` |

数据流（`pipeline.run()` 里顺序执行，无并发）：

```
广告导出 CSV/TSV（或剪贴板）
  └─ state_builder.load_rows()  → TermRow        全部算术在这里发生
  └─ rule_layer.judge_all()     → Verdict        主路径，可追溯
  └─ jev_shadow.judge_all()     → JevVerdict     影子层，默认 dry-run
  └─ compare.compare()          → Comparison     分歧检测 / 处置
  └─ pipeline.run()             → pipeline-output.json（meta / summary / rows）
  └─ bitable_sync.sync()        → 飞书多维表格记录
```

**事实**：全仓库**零第三方 Python 依赖** —— CI（`.github/workflows/ci.yml`）里没有 `pip install`
这一步；HTTP 用标准库 `urllib.request`，测试用 `unittest`，调外部命令用 `subprocess`。
唯一的外部运行时是 Node（只给 `amazon-ads-optimization/scripts/ads_opt.mjs` 用）。
45 个词的 live 调用（每个词 3 个问法）用时 57 秒（见 `docs/04-阈值标定.md`）。

## 二、核心模块

### 2.1 `state_builder.py` —— 算术的唯一发生地

- **`Economics`**：`contribution()` = 售价 − 成本 − FBA − 头程 − 售价×佣金率 − 售价×退货率×退货损失率；
  `break_even_acos()` = `contribution() / price`；`affordable_cpc(cvr, target)` = 售价 × CVR × 目标 ACoS。
- **`TermRow`**：一个搜索词的完整状态，构造时（`__post_init__`）算 `acos / cvr / ctr / cpc`，再调 `refresh()` 算 `click_threshold`。
- **`load_rows()`**：读 CSV/TSV → 列名别名归一 → 数字清洗 → 回填品类兜底 CVR。分隔符自动判断；
  必需列只有 `term / clicks / orders / spend`，缺则报错；`_num()` 去掉 `$`、`,`、`%`、`¥`，把 `""`、`-`、`--` 当 0。

| 派生量 | 公式 | 位置 |
|---|---|---|
| 实测 ACoS | `spend / sales`；无销售额时记 `-1`（下游显示「无成交」） | `TermRow.__post_init__` |
| CVR / CTR / CPC | `orders / clicks`、`clicks / impressions`、`spend / clicks` | 同上 |
| 动态点击阈值 | `max(5, round(1 / effective_cvr))`；本词 CVR＞0 用本词，否则用品类兜底 CVR | `TermRow.refresh()` |

**两个必须知道的细节（事实）**：

1. **`fallback_cvr` 必须靠 `refresh()` 重算。** 它是**品类级**参数，只有读完整张表才知道 ——
   `load_rows()` 末尾用「全量订单 ÷ 全量点击」算出再回填，而构造时它还是 0。回填后**必须再调一次
   `refresh()`**。代码注释写明这是踩过的 bug：不重算的话 `click_threshold` 停在 0，等于「永远不判断」，
   零单词会全部被误判成「保持」。
2. **`current_bid` 没有登记进 `COLUMN_ALIASES`**（该表只有
   `term / campaign / match_type / impressions / clicks / spend / sales / orders` 八项），
   而 `load_rows()` 却调 `get("current_bid")` —— 所以**报表里的出价列永远读不到**，
   `当前出价` 恒等于命令行 `--bid`。（核对代码时发现，见 §六）

### 2.2 `rule_layer.py` —— 可追溯的硬阈值

`judge(row, econ, target_acos)` 按**固定优先级**依次比较，命中即返回：

| # | 条件 | 动作 | 优先级 |
|---|---|---|---|
| 1 | 订单为 0 **且** 点击 ≥ 动态阈值（阈值 > 0） | 否定 | P0 |
| 2 | 转化速率 ≥ 2 单/周 | 加价（收割） | P1 |
| 3 | ACoS > 盈亏平衡线 **且** 点击 ≥ 20 | 降价 | P0 |
| 4 | 目标 ACoS < ACoS ≤ 盈亏平衡线 **且** 点击 ≥ 20 | 降价 | P1 |
| 5 | 点击 < 动态阈值 **且** 订单为 0 | 保持 | P2 |
| 6 | ACoS ≤ 目标 ACoS × 0.7 | 加价 | P1 |
| 7 | 以上都不命中 | 保持 | P2 |

两条**顺序敏感**的设计（事实，代码里有注释）：**「收割」必须排在「ACoS 超标就降价」之前** ——
依据 `verification.md` V17，稳定转化但 ACoS 差的词恰恰最需要独立活动（现在共享出价，你没法单独调它的价，
先判降价只是治标）；**「样本不足 → 保持」排在 ACoS 判定之后**，已完成转化的词不会被这条拦走。

**动作空间（事实）**：`Verdict.action` 是 `Literal["加价", "降价", "暂停", "保持", "否定"]`
—— 规则层**永远不会产出「暂停」**；「收割」也**不是**独立取值，而是用「加价」承载，理由只写在 `reason` 文案里。

### 2.3 `jev_shadow.py` —— 影子层

接口事实：端点 `https://openrouter.ai/api/alpha/decisions`，模型 `typesafe/jev-1.13`，
Key 走环境变量 `OPENROUTER_API_KEY`。代码注释特别写明：**该模型不能走 `chat/completions`**；
decisions 端点在 alpha 路径下，**没有 `/v1`**。三个问法（`QUESTIONS`）：`动作`（choice）、
`无效花费`（noul）、`紧迫度`（score）。

| 函数 | 做什么 |
|---|---|
| `judge(term, state, dry_run=True)` | `dry_run` 时**不联网**，直接返回动作 `未接入`、门控 `dry_run`；否则 `_call()` → `parse_answers()` |
| `_call(state, timeout=120)` | POST 到 decisions 端点。**5xx / 429 / 网络超时**最多尝试 3 次（退避 2s、4s）；4xx（除 429）不重试 |
| `parse_answers(term, resp)` | 纯函数，把原始响应解析成 `JevVerdict`，便于单测 |
| `_gate(action, confidence, waste_prob)` | 分动作阈值 + 硬约束；`judge_all()` 逐个词串行调用 |

**解析里踩过的字段名坑**（代码注释 + `CHANGELOG` 都有记）：`noul` 的值在 `"noul"` 字段里、
**不是** `"probability"`；`score` 在不同版本可能是 `score / level / value / rating`，要逐个尝试；
`urgency` 与 `waste_prob` 解析出来后必须**一路透传**到 `Comparison`，中途丢一次就永远是 `None`。

**分动作门控阈值（`GATE_THRESHOLDS`）**：保持 0.60 / 降价 0.80 / 加价 0.85 / 否定 0.85 / 暂停 0.90，
未知动作兜底 `DEFAULT_THRESHOLD = 0.70`（来源见 [`04-阈值标定`](../04-阈值标定.md)）。
**硬约束**：`无效花费概率 > 0.80`（`WASFUL_REVIEW_GUARD`）且动作是「否定」或「暂停」→ 强制 `review`。
**判断口径写在 `INSTRUCTIONS_ACTION` 里**（六条，按 ACoS 相对盈亏平衡线 / 动态点击阈值 / 样本量分级），
不写在 state 里 —— 理由见 §四 4.4。

### 2.4 `compare.py` —— 分歧检测

`compare(rule, jev)` 返回 `Comparison`（含 `是否分歧`、`处置`、`备注`）。分支顺序：

1. **Jev 未接入 → 立即返回**，处置固定「待标定」。代码注释写明：不提前返回会继续落入下面的
   高风险分支，把「待标定」错误覆盖成「人工复核」—— 这是实跑发现的 bug。
2. 两层动作相同 → `diverged = False`；不同 → 查 `EQUIVALENT` 表，命中为「强度分歧」，否则「方向分歧」。

`EQUIVALENT` 只有三组键：`(降价,否定)`、`(加价,保持)`、`(保持,降价)` —— **这是一张有方向的表**，
反向组合会落进「方向分歧」（见 §六）。

处置规则（代码顺序）：① 有分歧 → **人工复核**；② 无分歧且任一层是高风险动作（暂停 / 否定）
→ Jev 门控是 `auto` 才「自动执行」，否则「人工复核」；③ 无分歧、规则层 `P0` 且 Jev 门控 `review`
→ **人工复核**（并补一条备注）；④ 其余 → **自动执行**。

`summarize(rows)` 产出 `总词数 / 已接入 Jev 词数 / 分歧数 / 分歧率 / 自动执行 / 人工复核 / 待标定`。

### 2.5 `bitable_sync.py` —— 落到表格

| 元素 | 作用 |
|---|---|
| `SYNC_FIELDS` | 24 个字段清单，与 `base-schema.json` 一一对齐 |
| `SELECT_FIELDS` / `VALID_SELECT` | 6 个 select 字段（站点/匹配方式/规则层动作/规则层优先级/Jev动作/处置）；白名单外的值**跳过该字段**，不让整批写入失败 |
| `RATIO_FIELDS` | 比例类字段（目标ACOS / 实测ACOS / 盈亏平衡ACOS）按小数写入，四舍五入到 4 位 |
| `_to_record(row)` | 单行 → 字段映射；`None` / 空串 / `未接入` / `dry_run` 跳过；select 值包成**数组** |
| `build_payload(rows)` | 包一层 `{"create_records": [...]}` |
| `sync(...)` | 调 `lark-cli base +record-batch-create ... --as user --format json`；`dry_run=True` 时不调 CLI，只返回 count |
| `_resolve_cli()` | 定位 `lark-cli`（Windows 优先原生 `.exe`，理由见 [`07-集成与载体`](07-集成与载体.md)） |

### 2.6 `pipeline.py` —— 编排入口

`run(args)` 的顺序：构造 `Economics`（百分号参数 ÷ 100）与 `target` → 取数（`--input` 是文件路径就用文件；
是 `clipboard` / `clip` 就走剪贴板并**先快照落盘**）→ `load_rows()`（空则报错退出）→ `rule_judge_all()`
→ 逐词构造 `{"term":..., "state":...}` → `jev_judge_all()` → 逐词 `compare()` → 组装 `rows`。

**一个关键约定（事实）**：`rows` 里每行的**字段名就是多维表格的字段名**（`SYNC_FIELDS` 与 pipeline
输出键名一致），同步层不需要再做一层映射。

CLI 参数（`main()`）：`--input`（必需）、`--price`（必需）、`--out`（默认 `output/pipeline-output.json`）、
`--cost` / `--fba` / `--first-leg`（默认 0）、`--commission-rate`（默认 15）、`--return-rate`（默认 0）、
`--target-acos`（默认 25）、`--running-days`（默认 30）、`--bid`（默认 0）、
`--out-clipboard`（把结果摘要写回剪贴板）、`--jev {dry-run,live}`（默认 `dry-run`）。
带 `%` 语义的参数（`--commission-rate` / `--return-rate` / `--target-acos`）传的是百分数，代码里除以 100。

### 2.7 辅助模块

- **`clipboard_io.py`**：只在 Windows 可用（`available()` 检查 `os.name == "nt"` 与 PowerShell），
  用 `Get-Clipboard -Raw` / `Set-Clipboard`；**必须显式把 PowerShell 控制台编码设成 UTF-8**，
  否则中文按系统 OEM 代码页（简中 GBK/936）读写会乱码；写入走 stdin，避免命令行长度与转义问题。
- **`sweep.py`**：独立标定脚本，读 `output/jev-redhen-45.json`，在 0.50~0.90 九个阈值上扫描，
  输出覆盖率 / auto 子集一致率 / review 子集一致率 / 高风险误放，并比较一致组与分歧组的置信度分布。
  它用「与规则层是否一致」当代理指标（没有人工标注）。

## 三、怎么跑起来

**前置条件**：跑 dry-run 只需 Python 3.10+（无第三方依赖）；跑 JS 版规则层要 Node 18+；
读/写剪贴板要 Windows + PowerShell；同步到表格要本机装了并登录过 `lark-cli`；
`--jev live` 要环境变量 `OPENROUTER_API_KEY`。

**路径 A：dry-run（默认，不联网，不花钱）**

```bash
python src/pipeline.py \
  --input examples/input-sample.csv \
  --price 39.99 --cost 8 --fba 7.5 --first-leg 3 \
  --commission-rate 15 --return-rate 5 \
  --target-acos 25 --running-days 30 --bid 0.85 \
  --out output/pipeline-output.json
```

期望输出（实测）：`输入行数: 7　已接入 Jev: 0　分歧: 0　自动执行: 0　人工复核: 0　待标定: 7`。
**判读要点（事实）**：dry-run 下 Jev 列是「未接入」、处置列全部是「待标定」，
但**规则层结论、依据、优先级全部照常产出** —— 这是设计如此，不是没跑通。

**路径 B：live（真调 Jev）**

```bash
export OPENROUTER_API_KEY=sk-or-...          # Windows: $env:OPENROUTER_API_KEY = "..."

python src/pipeline.py \
  --input work/dataset-redhen-45.csv \
  --price 29.50 --cost 6.20 --fba 5.40 --first-leg 2.10 \
  --commission-rate 15 --return-rate 3 \
  --target-acos 25 --running-days 30 --bid 1.50 \
  --jev live --out output/jev-redhen-45.json

python src/sweep.py                            # 接着扫阈值、出曲线
```

**纪律（事实，来自本仓库的 `docs/01-定位与边界.md` / `docs/04-阈值标定.md`）**：`--jev live` 的前提是**你已经用自己的数据做过影子标定**
—— 置信度阈值不可跨 state 形状迁移（实测 state 从 630 涨到 26,200 token，置信度漂 ±0.33）。

**路径 C：剪贴板**

```bash
# 让剪贴板当输入（RPA 场景）：先把报表复制到剪贴板
python src/pipeline.py --input clipboard --price 39.99 --out output/from-clipboard.json

# 把结果摘要写回剪贴板（写之前会先把原剪贴板内容备份成文件）
python src/pipeline.py --input examples/input-sample.csv --price 39.99 --out output/x.json --out-clipboard
```

**落表与跑检查**

```bash
python src/bitable_sync.py --base-token <token> --table-id <id> \
  --input output/pipeline-output.json --dry-run      # 只数记录
python src/bitable_sync.py --base-token <token> --table-id <id> \
  --input output/pipeline-output.json --as user      # 真写入

python tools/run_checks.py                              # 一键：单测 + 仓库卫生 + 端到端干跑
python -m unittest discover -s tests -v                 # 只跑单测
```

CI 在 Python 3.10 / 3.12 上跑同样的检查，并额外断言：dry-run 输出里 `总词数 = 7`、`待标定 = 7`、
`自动执行 = 0`、`人工复核 = 0`，且**每一行都必须有非空的 `规则层依据`**。

## 四、关键设计决策（为什么）

**4.1 为什么算术全部外置，不交给模型。**
事实依据：Jev **不是计算器、不可靠计数**（误差随规模增长），也**不做日期比较**（把日期当文本读）。
做法：ACoS / CVR / CPC / 动态阈值 / 运行天数全部在 `state_builder.py` 算完，只把结果传给它。
为什么：让模型做算术，出错时就分不清是「判断错」还是「算错」，可追溯性直接断掉。

**4.2 为什么 state 要裁剪。**
事实依据：Jev 有 **context rot** —— 无关内容会扭曲置信度；实测 state 从 630 涨到 26,200 token（41 倍），
选中的动作 10/10 没变，但置信度**漂 ±0.33**。做法：`to_jev_state()` 只输出判断需要的字段
（站点、目标ACOS、盈亏平衡ACOS，加「本次判断对象」下的关键词/匹配方式/曝光/点击/花费/销售额/订单/
运行天数/当前出价/实测ACOS/CVR/CPC/动态点击阈值），**绝不整表塞进去**。
为什么：门的开合靠置信度，而置信度最怕无关内容 —— 裁剪不是省 token，是**保精度**。

**4.3 为什么选零依赖。**
事实：项目定位是**参考实现**，不是生产工具；CI 里没有装依赖这一步；只要求 Python 3.10+。
推断（本文作者判断）：换来三件事 —— ① 「照着跑起来」的门槛只剩一个 Python；② 没有依赖漂移，
一年后还能原样复现；③ 代码量小，改起来不用先理解框架。代价是没有并发、没有重试框架、
没有类型校验，这些都得自己写。

**4.4 为什么判断口径写在 `instructions` 里。**
事实依据：`jev-decision-layer` 实测 —— 只删掉 `instructions` 里的口径，同一判断的 `noul` 从 0.59 掉到 0.33。
事实案例：第一版只写「按目标 ACOS 口径」而**没说口径是什么**，结果 12 个词里 10 个被判「暂停」
（连 ACoS 26% 的健康词也是），分歧率 91.7%；把六条判据显式写进 `INSTRUCTIONS_ACTION` 后降到 33.3%、
自动执行从 1 升到 7。为什么：`criteria` 只告诉模型每个动作**是什么**，不告诉它**什么时候该选哪个**，
缺了后者模型会退化成最保守的选项。

**4.5 为什么规则层是主路径、Jev 是影子层。**
见 [`01-定位与边界`](../01-定位与边界.md)。一句话：广告优化最需要的是
**可解释性**，而黑盒概率给不了；影子的价值在于**它不同意的时候**，不在于它同意。

**4.6 为什么默认 `dry-run`。**
事实：`--jev` 默认 `dry-run`，`judge()` 在 dry-run 下直接返回「未接入」。为什么：置信度漂 ±0.33
意味着拍脑袋定阈值会**两个方向同时出错** —— 清晰案子虚高（本该复核的被自动执行）、
模糊案子崩塌（本该执行的被推进人工队列）；而这两种错误都看不见，因为置信度本身就是你以为
用来判断「该不该信」的那个数。

**4.7 为什么让输出 JSON 直接对齐表格字段名。**
事实：`SYNC_FIELDS` 与 `pipeline` 输出的键名逐字相同，同步层不做字段映射。
推断（本文作者判断）：中间少一层映射，就少一类「字段名对不上但没人发现」的 bug；代价是字段改名要同改多处。

## 六、代码核对发现（原文档没写清的点）

1. **`current_bid` 别名缺失**：`COLUMN_ALIASES` 里没有这一项，`load_rows()` 却调 `get("current_bid")`
   —— 报表里的出价列永远读不到，`当前出价` 恒等于命令行 `--bid`。
2. **「收割」在代码里回落成「加价」**：动作空间没有「收割」这一项，收割分支返回 `action="加价"`，
   只有 `reason` 文案写了「建议独立 Exact 活动」。表里「收割」和普通加价在这一列长得一样。
3. **`EQUIVALENT` 是单向表**：只登记 `(降价,否定)`、`(加价,保持)`、`(保持,降价)` 三个键，
   反向组合（如 `(否定,降价)`）会判成「方向分歧」而非「强度分歧」。
4. **门控不覆盖「两层一致 + P1/P2 + gate=review」**：处置规则里除高风险动作和 `P0 + review` 外，
   其余「无分歧」情形直接给「自动执行」—— 即一个 P1 的词即使 Jev 门控为 `review`，
   只要两层动作相同仍标「自动执行」。是设计取舍还是疏漏，代码里没有说明。
5. **未知 choice 静默变成「保持」**：`parse_answers()` 用 `ACTION_EN2CN.get(choice, "保持")`，
   模型返回没见过的选项时会被静默映射成「保持」，有可能被误判成「两层一致」。
6. **加价分支没有最小订单数下限**：`rule_layer` 第 6 条只要求 `acos >= 0 and acos <= target * 0.7`
   （`acos >= 0` 隐含销售额 > 0）；而 JS 侧 `ads_opt.mjs` 的提价分支是 `orders >= 1 && acos <= targetAcos * 0.7`。
7. **Python 与 JS 的收割判据不一致**：`rule_layer` 用**转化速率**（`orders / days * 7 >= 2`，≥2 单/周），
   `ads_opt.mjs diagnose` 用**绝对订单数**（`d.orders >= 2`），没按周归一 —— 同一个词两边可能给不同结论。
8. **`VALID_SELECT["Jev动作"]` 不含 `未接入`，但 `base-schema.json` 的选项里有它**：
   目前没暴露问题（`_to_record()` 更早就把 `未接入` 过滤掉了），但两处白名单不一致，改代码时容易踩。
9. **`Verdict.layer` 字段没有输出**：`as_row()` 不返回它，表里也就没有「层」这一列，按层筛选没有抓手。
